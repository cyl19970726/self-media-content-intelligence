# 博主级新工作流实跑与验收

## 使用目标与边界

用户要求先通过完整博主研究和 session-forensics 检查新工作流的有效性、稳定性与效率，再重分析已有博主；后续新博主也纳入同一接入流程。主 Agent 必须实际阅读工作台，不能以任务成功、Schema 通过或 Reviewer 无意见代替内容验收。

首个样本为 AI硬件情报局，沿用已采集素材与冻结选样。这里的完整博主研究是「观察作品库 + 全部深读选样重新构建 + 独立复核 + 跨帖综合」，不意味着逐篇深读作品库的全部作品。旧报告保留，新版本有明确来源关系。

## 评估方法

1. 启动前保存当前报告引用、批次、选样、来源素材和工作流版本；显式配置模型。生产调用限定目标 creatorRunId，避免领取其他博主遗留任务。
2. 检查冻结输入是否覆盖整套业务 skill（引用、脚本、Schema 等），实际模型是否读到相关材料，检查重建时是否携入旧候选。存在文件不等于已经阅读。
3. 按单帖记录来源核对、Builder、Reviewer、修订与登记；区分技术失败、未发现问题、提出意见、已修订未复核。Reviewer 不改写正文，修订需要逐项处置。
4. 综合读取本轮全部深读选样，并核对每条跨帖结论的逐帖支持、反例、分母和不确定性。不把历史批次中的旧报告无说明混入新结论。
5. 主 Agent 在页面阅读，抽查重要断言与原材料，记录实际获得的知识、仍缺的内容、页面不可达信息。审计说明抽查范围，不冒充全量内容验证。
6. 用实际调用数、耗时、用量、失败和有效修订衡量效率。SDK 日志与 Codex rollout 的字段不同；无法解析的指标记未知，不能记成零。

## 基线运行暴露的问题与干预

- **角色指令冲突**：共享包原来的“选定 operator 文件”模式虽然交付了完整 skill 包，却额外要求读取主 `SKILL.md`，与 Builder 的角色入口发生冲突；真实 trace 证实 Builder 阅读了该入口。共享仓库提交 `67c8d3e` 分开原生 skill 入口和 operator 入口，并将已知包内源路径投影到冻结副本；保留完整 references、scripts、assets、schemas。回归验证通过，当前基线继续使用旧 vendor，下一代运行再切换。
- **调度版本遗漏**：队列的控制步骤识别停留在旧版，漏掉当前 post v7 / synthesis v6。已生成单帖的父流程因此可能在其他 Builder 占满槽位时不能推进。修正后控制步骤可独立推进，并在普通待执行任务间优先复核和修订；仍受原模型并发限制。完整工程 `verify` 通过：682 项项目测试、62 项共享工作流测试，1 项项目测试环境跳过；不代表内容验收。
- **OCR 失败未恢复**：当前基线已落盘的前 4 篇共 165 帧均为 `failed/nilError`。同一原帧在宿主使用相同 macOS Vision 参数成功识别 8 行，说明不是原图没有文字。原 host 恢复函数只检查 frame ID 覆盖，误把完整失败结果当终态；正在修复宿主一次恢复及 Builder 对新增证据的有界消费。历史 creatorRun 的 99 份 / 3693 帧属于更早多轮积累，不能当作本轮样本数。
- **内容还原问题**：Host 已实际读首篇新候选的三大 Lens，抽查已提取画面与字幕。报告将“滑块两个部件”与“三条柔性条带”误判为同一对象的数量冲突；把原帖明确提到的设计参数流程归入未知，导致知识还原缺漏。这些问题封存在私有 Host 阅读记录，没有预先提供给独立 Reviewer，用于观察其自行发现能力。
- **失败恢复语义**：一次模型容量不足发生在候选生成前；输入正常，未进入内容校验，usage 未知。标准 API 先重试 child，但已失败 parent 不会自动恢复，需 child 成功后再重试 parent 的调用步骤；已有两步恢复回归测试。该重试在真正再次调用模型前，随本次系统缺陷干预取消，故不能宣称生产恢复已经成功验证。

发现系统 OCR 缺陷后，通过标准取消入口停止尚未生成的项目，保留已经开始的项目继续独立复核。取消时有一项恰好开始，实际为 **5 篇已开始 / 9 篇未开始取消**。原合同仍是 14 篇，本轮不能标记为完整博主研究，也不能将旧综合当作新结论。没有删除失败尝试或旧产物。下一轮使用新的 workflow revision 与共享包版本，单独记录有效性和时延。
