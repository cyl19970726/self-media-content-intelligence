# 《喂饭教程！小白1分钟做电影特效！》内容重建

本报告只来自已通过 schema 与证据引用检查的 `reconstruction.json`。按任务约束，没有生成独立 `evaluation.json` 或 `gate-report.json`，因此不使用 `READY_FOR_DOWNSTREAM_USE`。

## 这条18秒视频实际上讲了什么

视频用一个极短的“承诺—对照—三步界面—结果—评论CTA”结构，让观众相信在家用AI也能做出科幻大片感。

0–9.1秒，上下分屏固定标为“AI生成”和“实拍”。上方是装甲人物、绿色科幻枪战和专业摄影设备，下方是居家环境中的真人简易装甲、室内枪战和家用摄影设备。口播先说传统大片需要“巨额成本和复杂技术”，再反转为“现在你用AI在家也能拍好莱坞大片，操作非常简单”。这段主要是效果与门槛的视觉类比，不是软件操作。[证据：00:00–00:09，DENSE-0002、DENSE-0004、DENSE-0010、DENSE-0013]

9.2秒以后，画面固定显示大标题：“1分钟做科幻大片 / 小白有手就行！” 这是视频内明确提出的承诺，但不是计时结果。更关键的是，9.25秒同一画面右侧队列面板写着：`Your video is in queue and will start in a few minutes.`——任务被告知“几分钟后才开始”，与“一分钟做成”构成直接字面张力。[证据：TARGET-0161；9.25秒UI审阅裁切]

## 可见的真实输入、UI和步骤

口播把工具称为 Runway，但取景内没有读到“Runway”品牌字样；UI自身可读到 `Sessions`、`Prompt`、`Presets`、`Gen-3 Alpha` 等字段。应把“作者口播命名为 Runway”和“UI可见 Gen-3 Alpha”分开记录。画面没有展示选择 Gen-3 Alpha 的动作，也不能擅自补成精确产品版本。

视频中实际可见的编辑时序是：

1. **队列中的输入视图**（约9.20–10.75秒）：9.20秒帧已出现真人输入与 `In queue` 状态，9.25秒放大帧再确认完整子文案。文件名为 `9月21日(1).mp4`，预览是一名红发女性在明亮居家环境讲话，播放器显示约 `0:04/0:10` 到 `0:05/0:10`；右侧完整状态为 `In queue / Your video is in queue and will start in a few minutes.`。同一视图下方已经存在填写好的提示词，并非空白输入页。[TARGET-0028/OCR-00139、TARGET-0161、TARGET-0030]
2. **提示词近景**（约11.5–13秒）：剪辑更近地展示已存在的提示词，没有展示逐字键入。英文原文为：`Sci-fi movie style, a female soldier sitting and giving a speech, cinematic texture, CG animation`。黄色中文条写：“科幻风格，女士坐着发表演讲，CG动画”。[TARGET-0054、TARGET-0084；OCR-00548]
3. **输入/结果并排页**（约13.35–15.2秒）：左侧仍是真人输入，右侧出现红发、黑色金属感服装的CG女性角色，在蓝绿色室内背景中讲话并抬手。结果播放器下方明确可见 `Extend` 和 `Lip Sync` 控件，但没有点击或已应用状态。[TARGET-0168；14.25秒结果控件审阅裁切]
4. **结果主视图**（约15.45–18.13秒）：结果占据播放器，顶部可见 `Gen-3 Alpha` 和提示词摘要，播放进度约从 `0:00/0:10` 到 `0:02/0:10`；顶部通知字面为 `You're ready to generate.`，不是“生成完成”。[TARGET-0041、TARGET-0046]

视频没有展示文件选择器、实际上传动作、提示词键入、点击生成、排队进度、完成日志、Gen-3 Alpha选择、Lip Sync应用、保存或导出。它给出了拍摄显示器后的剪辑强调顺序，而不是连续实时操作记录。仅凭这些画面也无法确认界面是live网页会话、预录录屏还是摆拍展示。

## 效果与因果能说到哪一步

视觉上可以确认：真人输入与红发科幻女兵结果被放在同一页面并排，提示词中的“女性士兵、演讲、电影质感、CG动画”与结果外观相符。因此，视频确实把这段CG结果**框定为**输入与提示词的产物。

但视频不能证明：

- 当前结果由画面中的 `9月21日(1).mp4` 和这条提示词在同一次连续操作中生成；
- 中间没有额外参数、源素材、后处理、隐藏点击、加速或剪辑；
- `In queue` 与后来的 `You're ready to generate.` 属于同一任务的完整状态链；
- Gen-3 Alpha由作者在当前流程中主动选择；
- 所示页面来自同一个live会话，而不是预录或摆拍；
- 可见的 `Lip Sync` 已被应用；
- 作者所说“一段视频就渲染好了”对应了画面中可见的真实完成日志。

正确表述是“视频展示了输入、提示词与结果的编辑后对应”，而不是“视频完整证明了这套输入在1分钟内生成了该结果”。

## “1分钟”和“小白有手就行”是否被证明

没有。原视频总长只有18.133秒，且多次切换分屏、队列视图、提示词近景、并排结果和结果主视图。画面既没有从生成触发到完成的连续计时，也没有完整进度或日志。

最强的反证不是单纯“缺少计时”，而是同屏字面冲突：固定标题说“1分钟做科幻大片”，队列子文案却说视频 `will start in a few minutes`。也就是任务被提示几分钟后才开始，而标题承诺一分钟完成。视频没有解释两者的计时起点、适用范围或如何同时成立。

所以，“1分钟”是固定大标题中的作者承诺，“很快”和“真的有手就行”是口播主张。视频本身没有建立真实生成耗时，也没有证明所有小白在所有条件下都能完成。

## Lip Sync与结果音频

结果区可见 `Lip Sync`，说明口型同步至少在界面上是一个独立后续分支。视频没有展示点击它，也没有显示应用后的状态。

对完整0–18.137秒解码波形做了可审计机器听检：AudioSet模型以2秒窗口、1秒步长覆盖19个窗口，并分别试听开场、输入/排队、结果揭示和结尾四段；同时用L–R残差辅助减少居中旁白的遮蔽。它不是人类听觉，原始概率与限制保存在 `audio-evidence/machine-listening-raw.json`。

四段听检结果：

- **0–9.1秒开场**：旁白在；Music在所有开场窗口被检测到。存在间歇性effect-like/打击候选，但低置信的whoosh、ding、ping名称不应按字面采用。
- **9.1–13.35秒输入与排队**：旁白和Music继续；辅助残差能量比开场低，generic Sound effect候选间歇出现。音乐没有在9.1秒转场处停止。
- **13.35–16.15秒结果揭示**：旁白和Music继续，四段中辅助残差能量最低；没有新声音来源能独立归因给屏幕中的CG结果。
- **16.15–18.137秒结尾**：旁白和Music持续到解码终点，辅助残差能量回升；短效果样候选仍是间歇性的，身份未知。

因此，非语音音频可写成“音乐跨四段存在，但能量变化；短促效果只见间歇性effect-like候选”。不能写成音乐音量恒定、同一曲目严格连续，或断言具体音效名称。

整条帖子文件有AAC音轨，机器听检在结果阶段听到的仍是帖子旁白和音乐，没有可独立归因的结果片段原声。这不等于结果无声：帖子混音可能遮蔽它，且 `Lip Sync` 可见但未展示应用。因此，结果是否有声音、声音内容是什么、是否与角色口型同步，都保持unknown。声道布局和静音段结构仍无本报告采用的证据，不能写成“stereo”或“无明显静音”。

## 最小可复述结论

这不是一份完整的“1分钟教程”，而是一条18秒的剪辑式展示：作者口播称在Runway上传10秒真人实拍，再用一条“科幻电影风格、女性士兵坐着演讲、电影质感、CG动画”的提示词；画面随后展示一个10秒红发科幻女兵CG结果，并用它支持“很快、简单、有手就行”的承诺。听检确认帖子音乐贯穿四段但能量变化，短效果样候选间歇出现；结果原声无法从旁白和音乐中独立归因。队列还明说任务“几分钟后才开始”；Gen-3 Alpha选择、live会话、Lip Sync应用、结果自身音频、真实生成耗时、完整操作、版本与账号门槛、因果链和导出均未被视频证明。
