# 这条「三小时零代码做乙女文游」视频，实际展示了怎样的开发流程

视频给出的表面故事很简单：作者说自己用 Claude Code 做了一款“大厂女工被裁后，在都市生存并与多位男性角色互动”的乙女文游，全程三小时、不写一行代码，还把提示词整理成了可复用模板。

但把口播、README、终端、规格文档、目录状态、外部生图界面、Finder 文件和预览前后状态合起来看，真正可复现的不是“一句大白话自动出完整游戏”，而是一条有人类准备、外部资产处理、代理实现、人工审阅和返修的工作流。

## 1. 先装客户端，再把 Claude Code 指向 Kimi K2

视频第一步是给 Claude Code 配置 Kimi K2 thinking API。

如果尚未安装 Claude Code，画面中的命令是：

```bash
npm install -g @anthropic-ai/claude-code
```

视频随后短暂展示了 Kimi CLI 的 README。这里有一条很容易因为画面停留时间太短而漏掉的精确安装命令：

```bash
uv tool install --python 3.13 kimi-cli
```

README 还给出两个后续动作：

```bash
kimi --help
uv tool upgrade kimi-cli --no-cache
```

第一条用于检查安装，第二条用于升级。需要注意：视频展示的是 README 指令，并没有在这一小段里连续证明三条命令都实际执行成功。

接着，作者进入 Kimi 开发者平台创建或获取 API Key，把密钥替换进终端配置片段。画面能读到的关键参数包括：

```bash
export ANTHROPIC_BASE_URL=https://api.moonshot.cn/anthropic
export ANTHROPIC_AUTH_TOKEN=<你的密钥>
export ANTHROPIC_MODEL=kimi-k2-thinking-turbo
export ANTHROPIC_DEFAULT_OPUS_MODEL=kimi-k2-thinking-turbo
export ANTHROPIC_DEFAULT_SONNET_MODEL=kimi-k2-thinking-turbo
export ANTHROPIC_DEFAULT_HAIKU_MODEL=kimi-k2-thinking-turbo
export CLAUDE_CODE_SUBAGENT_MODEL=kimi-k2-thinking-turbo
```

这些变量被追加到 `~/.zshrc`，随后加载配置并启动 Claude Code。视频没有公开实际密钥，这部分也不应从画面猜测或还原。

配置是否成功，视频并不只靠一句“你好”来判断。终端界面同时出现了：

- `Claude Code v2.0.31`
- 模型 `kimi-k2-thinking-turbo`
- `API Usage Billing`
- 英文 `hi` 往返
- 中文 `你好` 往返

这五项共同构成画面里的成功状态。不过，它们只能证明该会话能响应基础问候，不能替代后续编码、计费或完整功能测试。

## 2. 真正的输入不是一句“大白话”，而是一份详细规格

口播把提示词概括成“世界观、主角、剧情、玩法、数值等等”，但屏幕中的 `universal_game_prompt.md` 远比这五个词具体。

它要求一个单页应用（SPA），并规定了技术栈和设计方式：语义化 HTML5、Vanilla CSS、不使用 Tailwind、手写高级 CSS、现代玻璃拟态视觉、微交互、桌面与移动端适配；JavaScript 则要求 Vanilla ES6+、面向对象写法和独立状态管理。

系统层面，文档至少规定了：

- `GameEngine`：天数/时段、状态更新、Intro/Ending 分支、随机日常事件。
- 存档：使用 `localStorage` 自动保存和读取进度。
- 主角系统：核心数值、数值变化反馈、条件触发失败或 Bad Ending。
- `CharacterManager`：NPC 数据、约会/送礼/对话引起的好感变化、角色详情。
- UI：逐字对话、立绘切换、顶部日期/时段/核心数值栏，以及菜单或记录界面。
- 文件结构：`index.html`、`styles.css`、`game.js` 或拆分后的多个 JS 文件，以及 `assets/images/`。

这意味着，代理输出的质量很大程度上取决于人类事先把产品、系统、交互、视觉和文件结构说清楚。视频的“说大白话”更准确的理解是：人类可以用自然语言写详细规格，而不是没有规格。

## 3. 代理开始工作时，项目并不是空目录

这一点是流程归因里最重要的边界之一。

Claude Code 的终端总结显示，当前项目在代理继续实现前已经有：

- `/story`：完整游戏设计/剧情文档
- `/characters`：五个攻略对象的 JSON 文件
- `/assets/images`：游戏资源图片

同时，画面把下面两个目录标成空：

- `/gameplay`：游戏机制，目前为空
- `/image_pipeline`：图像生成管线，为空

因此，不能把屏幕上读到的故事、角色和全部素材都写成“Claude Code 在此刻从零生成”。视频只证明代理读取并分析了这些既有材料；它们是谁创建的、什么时候创建的、是否经过前一轮代理或人工编辑，都没有在连续画面中闭合。

可读的项目内容包括：25 岁女主被互联网公司裁员、虚构都市、乙女向加模拟人生和职场重生的组合；五位男性攻略对象及其年龄/职业标签；`energy`、`mood`、`pressure`、`money`、`career`、`social` 等核心状态；以及日程、行动、事件和互动的设计方向。代理的工作状态更接近“基于已有策划和角色材料继续实现代码、事件与交互”，而不是“面对空白目录生成所有内容”。

## 4. 美术资产来自另一套界面，中间有人类操作和文件交接

当文字和框架已有后，作者指出项目仍缺大量图片，尤其缺少角色形象。

随后视频硬切到一套未显示品牌的外部生图界面。它展示了多组角色结果，每组通常是四张同一角色的变体，并带有保存或下载类控件。这里不能从界面猜测具体平台、模型、参数或授权，也不能把一个四图变体组直接当成四个最终交付角色。

作者明确说这一步要“自己动手跑了放在文件夹里”。后面的 Finder `images` 目录证实了本地文件状态：除了两张中文命名的文件，还能看到类似下面的命名链：

- `protagonist_neutral.png`
- `lin_yushen_neutral.png`
- 其他 `*_neutral.png` 角色立绘
- `bg_street_rain.png`
- `bg_office_day.png`
- `bg_home.png`
- `bg_park_evening.png`
- `bg_convenience_store.png`
- `bg_bookstore.png`

因此，可观察的资产链条是：外部界面产生候选图 → 人类选择/保存或下载 → 人类命名并放入本地目录 → 再告诉 Claude Code 文件夹里已有美术资产 → 代理读取并集成。

视频没有逐个展示每张图的下载点击，也没有建立每个本地文件与某个候选格的完整溯源，但它足以否定“Claude Code 自动包办了外部生图、选择、下载和命名”的说法。

## 5. 交付物是本地浏览器 SPA，不是已发布手游

代理完成说明里明确写着：双击 `index.html`，在浏览器中运行。它还指向剧情文档、`characters/` 目录和可用于二次开发的 `universal_game_prompt.md`。

之后的视频预览确实呈现出一款视觉小说：顶部有日期/时段和多组数值条，画面包含背景、角色大图、女主缩略图和对话框；不同片段出现了不止一位男性角色与不同场景，对话也会向后推进。

但视频没有实际操作或验证这些功能：

- 存档与读档
- Bad Ending
- 随机事件
- 角色详情与好感互动
- 日程/行动菜单
- 响应式或移动端行为
- 托管、打包、应用商店发布

所以，这一阶段能确认的是“本地可预览的 HTML/CSS/JavaScript SPA 原型”。人类提示里虽然称它为“手游”，画面并没有展示原生移动应用、独立可执行程序或已经发布的游戏。

## 6. 人类还承担了编辑审阅和返修

作者说对话由 Claude Code 和 K2 编写，但自己“每句都认真看了”。她认为人物交流自然、有生活气息和情绪，甚至优于大部分编剧。视频确实展示了若干对话片段，但这种质量判断是作者主观评价，没有盲测、评分标准或外部评审，不能升级成客观结论。

更关键的是，作者没有接受第一版布局。旧画面中，大型角色图和场景、对话框叠在一起。她明确提出：对话时只保留对话框下面的缩略图，隐藏背景里的大人物图。

随后 Claude Code 读取项目并编辑：

```text
Desktop/乙女向大厂裁员文游_副本/styles.css
```

画面能看到绝对定位、底部定位、居中变换、`height: 85vh`、flex 末端对齐、`pointer-events: none`，以及用于隐藏对话状态大图的 `display: none !important` 一类规则。修改后的预览不再保留原先那种大型人物与场景重叠的构图。

这是一个完整的前—中—后链条：初版预览 → 人类发现问题 → 人类描述修改目标 → 代理读文件并改 CSS → 新预览。它说明这套流程的关键不是“一次生成”，而是人类审阅与代理返修。

## 7. 这条视频真正能证明什么

视频能证明的是：通过精确安装和环境配置、详细自然语言规格、既有项目材料、外部美术工具、人工文件管理、代理集成、浏览器预览和人工返修，可以快速形成一个可看的本地视觉小说原型。

它没有证明：整个过程严格只花三小时、绝对没有任何手写代码、屏幕中的所有文件都由同一个代理会话从零创建、三种题材都已经完成端到端游戏、零经验用户都能稳定复现，或所有规格里的游戏系统都已实现并测试。

终端、文档、外部生图、Finder 和预览之间存在多次硬切，路径、版本与时间也没有全程连续显示。因此，它们可以组成合理的工作流叙述，但不能被当成同一项目版本的取证级连续记录。

另外，源文件包含贯穿全片的 AAC 立体声音轨。信号检查能确认持续音频，但不能可靠把旁白之外的成分命名为某段音乐或某个音效；在没有更强证据时，这一层应保持未知。

最终，最准确的概括不是“AI 自动做完了一款独立手游”，而是：**人类提供规格、账号配置、既有材料、外部资产、文件整理、审阅和修改方向；编码代理负责在这些边界内生成、整合和返修一个本地浏览器原型。**
