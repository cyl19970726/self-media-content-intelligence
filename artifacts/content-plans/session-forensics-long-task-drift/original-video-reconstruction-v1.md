# Session Forensics 原有剪辑内容还原与案例选择

## 状态

`RECONSTRUCTION_STATUS: EVIDENCE_BACKED_PARTIAL`

本稿来自 ChatCut 项目 `长任务不偏离：Session Forensics` 的当前 V6 时间线、四段完整口播 transcript、原始总图/分图、31 个 motion graphic 名称及六个 composed timeline 取样帧。它已经足以还原原片的论证结构与案例，但尚未检查整条 7m33s 时间线的连续音轨、每个短暂画面和所有转场，因此不冒充 `video-content-reconstruction` 的完整 hard-gate 成品。

## 一句话：原片真正卖的是什么

原片卖的不是一个“判断 Agent 有没有空转”的小工具，而是一套**长任务的外部审计与持续守护机制**：当执行 Agent 因局部问题、上下文压缩和自建 Gate 越走越窄时，让另一个拥有全局物证视角的 Session 还原它实际做过什么、目标如何变化、产物是否一致，并把可执行纠偏意见重新发给执行者。

Session Forensics 的价值链是：

`执行痕迹 → 全局证据 → 裂缝定位 → 可执行纠偏 → 回传执行 Session → 周期复审`

## 原片的完整问题—解法结构

### 1. 用户问题：长任务看似一直工作，人却失去掌控

原片开头不是“Agent 没有产出”，而是：

- 长任务持续运行，人很难参与过程；
- 界面和工具一直有活动，不代表仍在朝最初目标走；
- 用户真正缺少的是判断方向是否偏离的能力。

### 2. 背后思想：执行者视角天然收窄

口播提出一个认知模型：人或 AI 一旦进入执行角色，注意力就会集中在“下一步怎么做、当前问题怎么解”，很少退后检查“这条路本身是不是正确”。

原片进一步说，推理能力更强的 Agent 往往更擅长规划、测试和复查，因此可能持续增加 CI/CD、Gate 与端到端验证。这里想表达的是：**局部专业性可能变成全局方向感的替代品。**

“写 100 行业务代码，却写 1,000 行验证代码”是原片的夸张化例子，表达 Gate 成本可能反客为主；它不是统计事实。

### 3. 第一个错误解法：让执行者自己审查自己

原片明确讲了一个失败方案：最初试图让同一个 Agent 自审，但执行者仍携带自己的局部上下文和既有判断。结果可能不是退出死胡同，而是围绕“审查”再建一套验证代码与 Gate。

这一步非常重要，因为它解释了为什么普通 self-review prompt 不等于 Session Forensics。

### 4. 核心解法：执行权与审计权分离

真正方案是再开一个独立 Session：

- 执行 Session 负责继续推进、解决当前问题和交付产物；
- 外部审计 Session 返回原始目标、读取真实执行历史、对比叙事与行为；
- 审计结果不是取代执行者，而是把纠偏报告发回执行 Session。

原片的中心句不是“让 AI 更聪明”，而是“给它一个独立视角”。

### 5. 产品操作：输入 Session ID，自动形成报告

当前剪辑保留了完整操作链：

1. 新建一个独立会话；
2. 调用 Session Forensics；
3. 复制要审计的 Session ID；
4. 外部 Session 读取历史并生成报告；
5. 将报告/纠偏消息回传给执行 Session。

素材池还保留了 `copy-session-id-focus`、`paste-input-focus`、`sent-request-focus`、`audit-response-focus` 等聚焦录屏，这些才是产品“怎么用”的真实视觉证据。

## 原片里的核心真实案例

### 案例身份

总图标题为：`一个 40MB 长任务，为什么需要外部 Session 审计？`

它是一条运行约三天、由项目大脑调度多个工程师和文档 Agent 的长任务。可见审计快照显示：

- 23,417 行记录；
- 19 次 Compaction；
- 2,979 次 Exec；
- 约 1,868 次 Wait；
- 工具输出中 Exec 65.5%、Wait 23.2%、List Agents 11.1%；
- 上下文地板约 +97%；
- 仅 16 次 Patch、涉及 9 个文件。

这些数字证明活动结构与规模，不自动证明所有活动无效。

### 审计发现 01：持续 Wait，调度大脑退化为进程保姆

主 Agent 原本负责调度和业务推进，但时间线显示大量 Wait/Thread 轮询。等待期间任务状态和业务结论没有相应变化，却不断消耗上下文。口播的核心判断是：持续负责被实现成了持续轮询。

### 审计发现 02：Revision 在增加，业务结论没有变

图中显示 Revision 1129→1163，但所对应的业务结论片段仍为相同的 A→B。它要说明的是：版本号、工具调用和状态更新可以形成“假进展”，必须检查目标产物是否真的物化。

### 审计发现 03：Gate 膨胀，小改动触发全量重审

原片指出，主 Agent 自建大量 CI/CD / Gate，并倾向于把 Candidate 当正式阶段；很小的代码变化也重新运行全量 Gate，而非只跑受影响的增量验证。这产生了高时间成本，并进一步占用上下文。

### 审计发现 04：状态没有物化，Compaction 后只能重新推导

全局进展主要留在 Host 的上下文里，没有形成稳定、可继承的外部状态。上下文压缩后，Agent 需要重新推导，旧的全局判断容易失效。这是“为什么看起来一直在忙，却反复重新理解任务”的更深层原因。

### 审计发现 05：Candidate 语义漂移

图中区分：

- Working Revision：工作中；
- Candidate：送审版本；
- Accepted Revision：正式通过。

原片发现 Candidate 被当成正式阶段，甚至像是每个 Commit 的状态。其意义是：术语一旦漂移，流程显示“通过”也可能是假象。

## Session Forensics 的方法论

原图把方法浓缩成五步：

1. **定位 Session**：找到被审会话与平台结构；
2. **量化 Metrics**：记录量、工具分布、关键比率；
3. **有界 Drill**：收窄时间窗、范围和证据样本；
4. **物证对质叙事**：比较“Agent 说自己在做什么”与“日志、文件、报告实际发生什么”；
5. **发消息回原 Session**：给出结论、可执行建议与附证摘要。

图上的压缩链为：`GB 级会话 → KB 级证据 → 可执行纠偏`。

当前 V6 又把它整理成三层审计：

- 工具审计：Wait 洪水、无效轮询、上下文浪费；
- 证据审计：实际产物与执行叙事是否一致；
- 目标审计：用户指令发生了什么变化、方向是否漂移。

## 产品最终闭环

原片最后不是停在“生成一份报告”，而是：

- 把报告发给原执行 Session；
- 让执行者后续避开已发现的问题；
- 对长任务建立每三小时一次的周期审计；
- 在执行持续进行的同时，外部 Session 反复检查方向并回传。

原口播还声称支持 Kimi Code、Claude Code、Codex，并能通过内部自成长机制适配其他 Agent；这是作者主张，当前剪辑没有逐个平台演示。原片也提到可以在额度耗尽或任务中断时，用会话历史做 handoff；这是第二产品场景，不是主案例。

## 哪个案例更适合新版

### 结论：40MB / 三天多 Agent 案例更适合做主案例

它比上一版使用的“剪辑任务反复改布局”更适合推销 Session Forensics，原因是：

1. **角色清楚**：项目大脑、工程师、文档 Agent，观众能理解什么叫长任务；
2. **代价可见**：三天、23,417 行、19 次压缩、2,979 Exec、约 1,868 Wait；
3. **裂缝具体**：进程保姆、假进展、Gate 膨胀、状态未物化、Candidate 漂移；
4. **只有外部审计容易发现**：这直接证明产品的独特价值；
5. **解法闭环**：输入 Session ID → 五步审计 → 报告回传 → 定时复审。

### 剪辑失败会话适合当第二层证据

`019ff003...` 的“内容必须放大、录屏仍不可读、同类要求反复出现”很有价值，但它更适合说明：Session Forensics 不只审开发，也能审创作和剪辑流程。它应作为跨领域补充或下一条案例，而不应取代原片的主案例。

## 上一版内容为什么显得没理解产品

上一版把产品压缩成了“活动量不等于目标闭合”的单一判断器，遗漏了：

- 执行者自审为什么失败；
- 执行权与审计权分离；
- 40MB 三天多 Agent 的完整案例；
- 五种可辨识的审计发现；
- 五步审计方法和 GB→KB→纠偏；
- 报告回传给原 Session 的动作闭环；
- 每三小时周期复审；
- handoff 与跨 Agent/平台适配场景。

它抓住了一个传播钩子，却把一个“长任务外部控制系统”讲成了一个“空转报警器”。

## 下一版应该先做的决定

不要马上把原片机械压到 60 秒。先在两种产品形态中选择：

- **90–120 秒 Hero Explainer**：保留问题、错误自审、角色分离、一个真实案例的 2–3 个发现、五步法和回传闭环；更适合完整推销产品。
- **45–60 秒案例短片**：只讲“调度大脑变进程保姆”这一条裂缝，用五步法快速证明，再把完整案例放到长版或文章；更接近 AI 红发魔女的传播节奏。

无论选哪一种，主角都应当是“外部审计发现了执行者自己看不到的裂缝”，而不是单纯堆数字或泛化 Agent 焦虑。
