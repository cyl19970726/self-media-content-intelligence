# Signal Room V3 — 产品需求文档（PRD）

## 1. 产品定义

Signal Room V3 是面向多平台内容运营者的「自媒体内容研究与起号决策工作台」。它不以一次分析任务或一份静态报告为核心，而以持续积累的研究对象为核心：帖子、博主、专题、证据、结论、内容模型、实验和发布复盘。

当前版本已经能够完成链接采集、公开指标整理、视频拉片和单次报告生成，但用户仍需在一张长报告中自行寻找结论、证据和下一步动作。V3 需要把这套能力重组为一个闭环：

`发现内容 → 建立样本 → 分析与对照 → 形成结论 → 生成内容 Brief → 发布 → 回填表现 → 更新认知`

## 2. 目标用户与核心任务

### 2.1 目标用户

- 同时运营小红书、微信视频号、抖音、YouTube 和 X 的个人创作者或小团队。
- 需要研究同行、专题和爆款机制的内容策划、编导与运营者。
- 希望利用真实内容样本建立账号定位和内容模型，而不是只获得泛化建议的人。

### 2.2 用户最需要回答的问题

1. 单条内容为什么表现成这样，哪些结论有证据，哪些只是猜测？
2. 同一专题里，表现好的帖子和不符合预期的帖子真正差在哪里？
3. 一个博主稳定服务谁、用什么内容系统、哪些能力可复制？
4. 研究得到的认识怎样转成下一条选题、脚本和可验收实验？
5. 内容发布后，真实表现怎样反过来更新原来的判断？

## 3. 产品原则

1. **一个页面只回答一个研究问题。** 单帖、多帖专题和博主是三种独立研究项目，不在一张长页中混合。
2. **先定义目标，再判断好坏。** 认知扩散、账号增长、内容资产和商业转化采用不同判定维度。
3. **没有对照，不下强结论。** 单帖必须对比作者或题材基线；多帖必须说明分组规则、观察窗口和样本边界。
4. **事实、观察、假设、未知严格分层。** 公开数据不能替代曝光、留存、转粉、留资或成交数据。
5. **结论必须可追溯。** 每条判断都能回到原文、指标快照、评论、时间码或画面帧。
6. **研究必须导向动作。** 可将结论保存为内容模型、生成 Brief、建立实验或加入发布复盘。
7. **平台共用一套研究语言，同时保留平台特性。** 小红书强调封面标题、搜索、收藏和人群语境；其他平台使用各自适配维度。

## 4. 信息架构

V3 主导航保留四个工作区：

| 工作区 | 主要对象 | 用户得到什么 |
| --- | --- | --- |
| 研究台 | 万能投递、研究项目、待决策队列 | 发起或继续一次研究 |
| 样本库 | 帖子、博主、专题合集、标签 | 保存和组织可复用样本 |
| 内容模型 | 成功结构、失败模式、脚本母版、平台打法 | 将研究结论沉淀为方法 |
| 发布复盘 | 内容 Brief、实验、已发布内容、指标快照 | 验证结论并更新认知 |

Notion 是团队知识与协作层，不是运行时数据源。V3 应允许把成熟的研究结论、内容模型和复盘摘要同步到 Notion；原始媒体、逐帧证据和计算过程保留在本地工作台。

## 5. 核心用户流程

### 5.1 万能投递

用户可以从网页、Codex 对话或 CLI 投递：

- 一条帖子链接或小红书分享文案；
- 2–100 条帖子链接；
- 博主主页链接；
- 一个关键词或自然语言研究问题；
- 已保存样本库中的帖子或博主。

系统识别输入后展示预览，并提供：

- 立即分析单帖；
- 加入现有专题或新建专题；
- 分析对应博主；
- 仅收藏到收件箱。

### 5.2 单帖分析

单帖项目回答“这条内容为什么表现成这样”。页面由以下区域构成：

1. 研究问题、当前目标与一句话判断；
2. 相对作者与同题材基线的位置；
3. 内容 X-Ray：人群、需求、承诺、钩子、脚本、画面、证据、CTA；
4. 可定位到时间码的拉片与转录；
5. 评论中的需求、异议、实践意图和后续内容需求；
6. 机制假设、反证、替代解释与缺失数据；
7. 可复用结构、不可照搬条件和下一条实验。

### 5.3 多帖／专题分析

多帖项目回答“同一问题中，什么真正区分表现好与差的内容”。专题既可以由用户手动添加链接，也可以由关键词研究生成候选样本。

分析前必须明确：

- 运营目标；
- 样本范围、平台、时间范围和观察窗口；
- 赢家、中位组和低表现组的定义；
- 是否控制作者体量、发布时间、内容形式、投流和内容时效性；
- 数据不足时不能回答的问题。

专题对照至少覆盖：目标人群、用户任务、选题角度、标题封面、内容形式、脚本结构、画面语法、证据密度、CTA、评论需求、搜索适配、互动结构和真实业务结果。

### 5.4 博主分析

博主项目回答“这个账号怎样持续服务一群人，以及哪些能力可复制”。输入主页链接后，系统采集公开主页资料及近期／代表内容，构建：

- 受众分群与用户任务；
- 账号承诺与定位；
- 内容支柱及其占比、表现和稳定性；
- 内容形式、视觉语法和脚本母版；
- 可信度与证据系统；
- 发布节奏、系列化和长尾；
- 爆款依赖、异常内容和失速模式；
- 评论需求、商业路径和私域／产品信号；
- 可复制能力、账号依赖和差异化起号建议。

用户提供的“人类最强编导”主页作为首个真实博主研究样例。分享文案中的“30.9 万赞与收藏”只能作为待验证输入元数据，不能直接作为分析结论。

### 5.5 从研究到复盘

用户可对任意结论执行：

- 保存为内容模型；
- 生成一个选题或脚本 Brief；
- 建立 A/B 或连续内容实验；
- 关联实际发布内容；
- 导入后台指标快照；
- 复盘后确认、修正或否定原假设。

## 6. 好与差的判定规则

| 目标 | 可使用的公开信号 | 需要账号后台数据才能闭环 |
| --- | --- | --- |
| 认知扩散 | 互动规模、速度、分享／点赞、作者／题材提升 | 曝光来源、覆盖人数、投流增量 |
| 账号增长 | 评论意图、主页相关公开信号（若有） | 主页访问、净增粉、转粉率、回访 |
| 内容资产 | 收藏／点赞、搜索信号、跨时间快照 | 搜索流量占比、7／30 日长尾、留存 |
| 商业转化 | 评论中的询价或行动意图 | 点击、私信、留资、成交、成本 |

系统不得生成跨目标的单一综合分。缺失数据必须显示为“未知”，不得当作零或失败。

## 7. 功能需求与验收标准

### R1 — 输入识别与项目创建

- 当用户粘贴单条帖子链接或分享文案时，系统应识别平台、对象类型和可提取标题，并在创建前显示输入预览。
- 当用户粘贴主页链接时，系统应创建博主研究项目，不得把主页误建为单帖任务。
- 当用户提交 2–100 条链接或一个关键词研究问题时，系统应允许创建多帖／专题项目。
- 当输入无法识别时，系统应保留原文并说明需要用户补充的最少信息，不得创建伪造样本。

### R2 — 研究项目与样本组织

- 当研究项目创建后，系统应保存项目类型、研究问题、运营目标、样本范围、负责人、状态和更新时间。
- 当同一帖子被多个项目使用时，系统应复用同一个帖子实体，并分别保存项目中的角色和纳入原因。
- 当用户从任意分析页添加样本时，系统应支持加入现有专题或新建专题，而不丢失当前页面状态。

### R3 — 单帖分析

- 当单帖拥有作者或题材样本时，系统应显示相对中位数、百分位和归一化互动结构；当基线不存在时，应明确表示不能判断异常程度。
- 当媒体可读取时，系统应提供真实镜头边界、时间码、代表帧和转录证据；当媒体不可读取时，应隐藏依赖媒体的结论并显示缺口。
- 当用户点击一条单帖结论时，系统应在证据检查器中展示其原始文本、指标、评论、画面或计算公式。

### R4 — 多帖／专题分析

- 当专题包含不少于 8 条可比帖子时，系统应允许建立赢家、中位和低表现分组，并显示分组规则与样本量。
- 当帖子发布时间或观察寿命不一致时，系统应优先使用同观察窗口指标或速度指标；无法校准时应显示偏差警告。
- 当系统输出“区分因素”时，必须同时展示支持样本、反例、效应方向和可能的混杂因素。
- 当样本不足或不可比时，系统应降级为探索性观察，不得输出稳定规律。

### R5 — 博主分析

- 当博主样本不少于 12 条且覆盖不少于 3 个发布时间段时，系统应输出内容支柱、形式系统、视觉语法、脚本母版、稳定性和爆款依赖。
- 当博主样本不足 12 条时，系统应展示样本不足，并限制稳定性和内容战略外推。
- 当用户查看任何内容支柱或脚本母版时，系统应列出代表帖子、高表现例、低表现例和证据。
- 当系统生成起号建议时，应区分可复制能力、账号身份依赖、资源依赖和建议差异化方向。

### R6 — 证据、结论与未知

- 当系统生成判断时，每条判断应具有 `fact`、`observation`、`hypothesis` 或 `unknown` 类型、置信度、证据引用和适用范围。
- 当证据存在反例或替代解释时，系统应与主判断同时展示，不得只保留支持性证据。
- 当用户发现结论不准确时，系统应允许人工修正状态、补充说明和保留修订历史。

### R7 — 内容模型与行动

- 当用户保存一条结论时，系统应允许将其转为成功结构、失败模式、脚本母版或平台打法。
- 当用户从研究项目生成 Brief 时，系统应引用来源结论，并声明必须保留的变量、可测试变量、风险和验收指标。
- 当实验缺少可采集的主要指标时，系统应标记为“数据阻塞”，不得声称实验可验收。

### R8 — 发布复盘

- 当用户关联已发布内容时，系统应记录平台内容 ID、发布时间、内容版本和关联 Brief／实验。
- 当用户导入多个时间点的指标时，系统应保留每次快照，不得覆盖旧值。
- 当复盘完成时，系统应允许确认、修正或否定原假设，并将结果回写到内容模型。

### R9 — 页面层级与响应式

- 当用户进入任一研究项目时，首屏应显示研究问题、目标、样本边界、关键结论和下一步动作，不以技术运行阶段为主要内容。
- 当视口宽度不小于 1280px 时，页面应同时容纳导航、主研究画布和证据检查器。
- 当视口宽度小于 1024px 时，导航应折叠，证据检查器应变为抽屉，页面不得横向溢出。
- 当研究内容较长时，系统应通过章节导航、筛选和钻取组织信息，不得依赖一张无限纵向长报告。

### R10 — 平台适配与数据边界

- 当平台为小红书时，系统应特别分析封面、标题、搜索意图、收藏价值、人群语境和评论需求。
- 当平台缺少某项公开指标时，系统应保持该字段为空并显示平台边界，不得进行跨平台错误换算。
- 当真实平台采集受登录或授权阻塞时，系统应保留项目和阻塞原因，不得使用演示数据替换。

### R11 — Notion 同步

- 当用户选择同步成熟结论时，系统应把研究摘要、内容模型、Brief 或复盘同步到对应 Notion 数据库。
- 当原始媒体和逐帧证据体量较大时，Notion 仅保存摘要、缩略图与本地报告链接，不复制全部运行数据。
- 当 Notion 同步失败时，本地项目状态和内容不得受影响。

## 8. 非目标

- V3 第一阶段不自动发布、点赞、评论、关注或发送私信。
- 不绕过平台登录、访问控制或风险限制抓取数据。
- 不用单条帖子证明因果关系或代表整个平台规律。
- 不在没有后台数据时判断真实留存、转粉、成交或投流回报。
- 不把标题关键词聚类直接称为完整的内容战略。
- 不让 Notion 成为运行时唯一数据源或存储大体量媒体证据。

## 9. 成功标准

- 用户从投递链接到获得第一条可追溯结论不超过一次完整分析流程。
- 100% 的结论具有类型、证据引用、置信度和适用范围。
- 多帖与博主项目中，用户可以从任何聚合结论钻取到代表样本和反例。
- 用户能在研究页内完成“保存内容模型”或“生成下一条 Brief”，无需复制粘贴报告。
- 研究项目、发布内容和复盘之间可追溯，形成至少一次完整学习闭环。
